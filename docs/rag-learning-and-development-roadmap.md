# RAG 学习与项目开发路线

> 整理日期：2026-07-10  
> 适用项目：AI Clothing Shopping Assistant System

## 1. 核心结论

1. 当前 RAG 的流程和数据边界设计并不弱，真正薄弱的是知识覆盖、真实向量索引和真实检索评测。
2. 现在不应该先凭感觉调参，应该先建立评测集、补充权威知识、重建索引并跑出基线。
3. MySQL 继续作为商品、SKU、价格和库存的事实源；RAG 只处理颜色、材质、洗涤、版型和场景等解释性知识。
4. 不需要把 MySQL 数据全量复制到向量库，向量库是语义索引，不是 MySQL 或 Redis 的替代品。

## 2. 当前项目盘点

| 项目 | 当前状态 |
| --- | --- |
| MySQL 商品 | 40 个 SPU |
| MySQL SKU | 233 个 |
| 商品属性 | 462 条 |
| RAG 原始知识 | 3 个 TXT，约 11.8 KB |
| RAG chunk | 34 个 |
| chunk 长度 | 27～242 字，平均约 115 字 |
| 真实向量索引 | 当前本地不存在 |
| Agent 检索数量 | `top_k = 3` |
| 相关性规则 | 余弦距离 `<= 0.7` |
| 回答模型温度 | `0.1` |
| 向量存储实现 | 本地 JSON + 全量余弦距离计算 |
| 已验证相关测试 | 33 个通过，但很多使用 fake RAG |

当前生产思路是正确的：

```text
MySQL 商品事实
-> Java 过滤 SKU 候选池
-> Python 解析语义偏好并重排序
-> RAG 可选补充颜色、材质、场景等解释
-> Python 只返回 Java 候选池内的商品引用
-> Java 再次校验商品引用
```

# 第一部分：个人学习与面试准备

> 本部分是个人能力提升任务，不等于项目开发需求。

## 3. 需要掌握的知识地图

### 3.1 完整 RAG 链路

```text
离线：
权威知识 -> 清洗 -> 语义切块 -> Embedding -> 向量索引 -> 版本和来源元数据

在线：
用户问题 -> 意图判断/查询改写 -> 检索 -> 过滤/重排序
-> 上下文组装 -> 大模型生成 -> 事实校验/引用/拒答 -> 评测与监控
```

重点理解：

- 知识库是原始权威资料，向量库只是可重建的派生索引。
- 文档和查询必须使用兼容的 embedding 模型。
- RAG 减少幻觉，但不能完全消除幻觉。
- 检索错误、弱证据、过期知识和模型忽略上下文都会产生错误回答。

### 3.2 大模型幻觉

面试回答：

> 大模型幻觉是模型生成了语言流畅，但无法被用户输入、知识库或工具结果支持的内容。大模型本质上是下一个 token 预测器，不是事实数据库。工程上应该通过结构化事实源、RAG 检索、相关性过滤、来源引用、保守拒答、答案校验和离线评测共同控制幻觉。

需要能举出的错误类型：

- 编造价格、库存、SKU 或售后政策。
- 知识库没有证据却给出确定结论。
- 检索证据与最终答案矛盾。
- 编造不存在的来源或引用。
- 使用过期知识回答实时问题。

### 3.3 RAG 调参

面试回答：

> 我不会凭感觉直接调大 top-k。我会先建立带标准来源和答案要点的评测集，区分检索失败和生成失败。检索阶段看 Recall@K、Hit Rate 和 MRR，生成阶段看 faithfulness、答案正确性和拒答准确率，同时观察延迟和成本。调整顺序是数据质量和切块，然后是查询改写、embedding、top-k、相似度阈值、metadata filter 和 rerank，最后才是 prompt 和生成参数。

需要掌握的参数：

| 层级 | 参数 | 核心影响 |
| --- | --- | --- |
| 数据 | chunk 大小、重叠、标题保留 | 上下文完整性与噪声 |
| Embedding | 模型和文本规范化 | 语义召回能力 |
| 检索 | `top_k` | 漏召回与噪声之间的平衡 |
| 检索 | 相似度/距离阈值 | 弱证据接受和拒绝 |
| 检索 | metadata filter | 限制领域、文档类型和版本 |
| 重排序 | 初召回数量、最终证据数 | 前几条证据的精度 |
| 生成 | temperature | 随机性，不能保证事实正确 |
| 系统 | fallback 条件 | 证据不足时是否拒答 |

### 3.4 MySQL、Redis 和向量库

面试回答：

> MySQL 是业务事实源，适合精确查询、事务和强一致数据。Redis 是缓存，用来加速已经可以精确定位的数据。向量库是语义索引，用来根据意思相似找文本。向量库不是 MySQL 的替代品，也不只是另一种 Redis。

# 第二部分：项目待开发事项

> 本部分是需要修改代码、知识资产、评测或运行配置的项目开发任务。

## 5. P0：让真实 RAG 可用、可评测

### 5.1 建立项目级 RAG 评测集

- [ ] 新增 30～50 个真实业务问题。
- [ ] 覆盖颜色、材质、洗涤、季节、版型、场景和超出知识范围的问题。
- [ ] 每个 case 记录预期意图、预期来源、预期 chunk、答案要点和是否应该拒答。
- [ ] 分离检索评测和答案质量评测。

验收标准：

- 评测不依赖 fake chunks。
- 能单独报告 Recall@K、错误接受率和拒答准确率。

### 5.2 补充权威知识

建议扩展领域：

- [ ] 校园、通勤、约会、旅行、运动等场景穿搭。
- [ ] 纯棉、羊毛、亚麻、聚酯、牛仔、羽绒等材质特性。
- [ ] 直筒、A 字、高腰、宽松、修身等版型解释。
- [ ] 颜色搭配、季节适配和叠穿原则。
- [ ] 洗涤养护和尺码版型的原则性说明。

知识质量规则：

- 每条知识必须有可追溯来源。
- 不把实时价格、库存、SKU 或上下架状态写进 RAG。
- 数据量不是目标，目标问题覆盖率才是目标。

### 5.3 建立真实向量索引

- [ ] 配置当前 embedding 服务所需环境变量。
- [ ] 从本地权威知识重建 `simple_vector_store.json` 和 `vector_store_meta.json`。
- [ ] 校验 chunk 数量、源文件 hash、embedding 提供方和构建时间。
- [ ] 使用真实问题验证检索结果。

验收标准：

- RAG 启动时可判断索引是否存在以及是否过期。
- 评测命令可以在不使用 fake RAG 的情况下完成检索。

## 6. P1：基于评测调整检索

- [ ] 比较 `top_k = 1 / 3 / 5` 对 Recall@K 和噪声的影响。
- [ ] 采样相关和不相关 chunk 的距离分布，再决定阈值，不直接猜测。
- [ ] 检查当前关键词扩展是否提升召回或引入噪声。
- [ ] 为颜色、材质、洗涤和场景增加更精确的 metadata。
- [ ] 只有在普通检索无法达到评测目标时，才考虑文档 reranker。

验收标准：

- 每次参数修改都有评测前后对比。
- 不用增大 `top_k` 来掩盖知识缺失。
- 检索质量、延迟和成本同时可观测。

## 7. P2：强化幻觉防护

当前已有：

- 结构化事实和 RAG 解释知识分离。
- `retrieval_grader` 拒绝弱证据。
- 无证据时保守 fallback。
- Python 只返回 Java candidates 中的商品引用。

待开发：

- [ ] 向用户显示简洁的知识来源或引用。
- [ ] 保留答案结论与 `chunk_id`/来源的映射。
- [ ] 增加“答案是否能被证据支持”的 groundedness 校验。
- [ ] 增加过期知识、冲突知识和无来源知识的测试。
- [ ] 对真实模型回答进行小比例人工抽样。

## 8. P3：知识库更新和可观测性

- [ ] 将当前“必须上传固定 3 个文件”的限制调整为知识目录或清单驱动。
- [ ] 为文档增加 domain、source、version 和 effective_at 等元数据。
- [ ] 在健康检查或调试界面展示 RAG 是否 ready、chunk 数和索引版本。
- [ ] 索引缺失或重建失败时继续允许 Java 候选商品排序，但明确降级状态。

## 9. 当前不开发的内容

- 不把 MySQL 价格、库存和 SKU 全量复制进 RAG。
- 不在只有几十个 chunk 时引入 Milvus、Qdrant 或 Elasticsearch。
- 不在没有评测集时调整一大批参数。
- 不用降低 temperature 代替事实校验。
- 不在当前数据量下引入消息队列、CDC 或复杂增量同步。

## 10. 未来商品量扩大时的边界

只有当 SQL 候选召回无法满足大规模语义搜索时，才将稳定商品文本建立为二级向量索引：

```text
商品名称 + 描述 + 材质 + 风格 + 场景 + attribute_tags + spu_id/sku_id
-> 向量召回 ID
-> 回查 MySQL
-> 校验上下架、价格和库存
-> 生成最终候选池
```

即使进入该阶段，向量索引也只负责召回，MySQL 仍是最终事实源。

## 11. 推荐执行顺序

```text
1. 个人先跟踪两条真实请求链路
2. 项目建立 RAG 真实评测集
3. 补充权威解释性知识
4. 重建真实向量索引
5. 跑出当前 top_k 和阈值的基线
6. 根据评测调整切块、查询、top_k 和阈值
7. 增加来源引用和 groundedness 校验
8. 数据规模明显增长后再升级向量基础设施
```

项目面试总结：

> MySQL/Java 保证商品事实，Python 在 Java 候选池内做语义重排序，RAG 负责颜色、材质、版型和场景等解释性知识，证据不足时保守拒答。
